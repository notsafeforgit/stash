# Stash UI v3: Full Rewrite Plan

## Context

The current UI (`ui/v2.5/`) uses React 17, Bootstrap 4, React Router v5, Apollo Client 3.8, and TypeScript 4.8. The goal is a ground-up UI rewrite in `ui/v3/` using a modern stack, built as a proper PWA with first-class mobile and desktop support. The existing ~7K lines of framework-agnostic logic (GraphQL hooks, utils, filter models) have been copied into v3 and adapted. v2.5 stays frozen as fallback.

### Key Apollo 4 migration decisions

1. **No generated React hooks.** The `typescript-react-apollo` codegen plugin is incompatible with Apollo 4 (references removed/renamed types like `MutationFunction`, `BaseMutationOptions`). Instead, we use only the `typed-document-node` plugin. Generated documents like `FindScenesDocument` are typed as `DocumentNode<FindScenesQuery, FindScenesQueryVariables>`, so `useQuery(FindScenesDocument)` automatically infers all types.

2. **Import path changes:**
   - `ApolloProvider` -> `@apollo/client/react` (not `@apollo/client`)
   - `useApolloClient`, `useQuery`, `useMutation` -> `@apollo/client/react`
   - `TypePolicies`, `FieldReadFunction` -> `import type from "@apollo/client/cache"`
   - `ApolloError` -> `CombinedGraphQLErrors` (from `@apollo/client`)
   - `onError` handler: `({ error }) => { ServerError.is(error) && error.statusCode }` (unified error param)
   - `ApolloClient` is no longer generic -- no type parameter

3. **apollo-upload-client v19:** `createUploadLink` replaced by `UploadHttpLink` class: `import UploadHttpLink from "apollo-upload-client/UploadHttpLink.mjs"`

4. **`cloneDeep` removed from Apollo 4 utilities.** Replaced with `structuredClone()`.

## Phase 1: Architecture principles

These apply to every subsequent phase. The v2.5 codebase has significant structural debt — copy-pasted entity pages, a 3044-line god-object service file, ad-hoc state patterns, and no component reuse across entity types. The rewrite is the opportunity to fix this.

### Kill StashService.ts

The monolithic `StashService.ts` wraps every generated hook in a named function. With Apollo 4 + TypedDocumentNode, this entire file is unnecessary — `useQuery(FindScenesDocument)` gives you full type inference. No wrapper layer.

**Rule:** Components import query/mutation documents directly from `generated-graphql.ts` and call Apollo hooks inline. Small, focused hooks (e.g. `useSceneUpdate`, `useBulkSceneUpdate`) live next to the components that need them, not in a central service file.

### One generic list, not seven copy-pastes

v2.5's `SceneList`, `PerformerList`, `GalleryList`, etc. are 200-400 line files that repeat the same pattern: fetch → filter → paginate → render cards/table. They differ only in:
- The query document
- The filter mode and available criteria
- The card/row component
- Column definitions (for table view)

**Rule:** Build a single `EntityList<TData, TVariables>` component parameterized by a config object:

```ts
interface EntityListConfig<TData, TVariables> {
  query: TypedDocumentNode<TData, TVariables>;
  filterMode: FilterMode;
  extractItems: (data: TData) => { count: number; items: unknown[] };
  makeVariables: (filter: ListFilterModel) => TVariables;
  renderCard: (item: unknown) => ReactNode;
  columns?: ColumnDef[];         // for table view
  defaultSort?: string;
  defaultView?: View;
}
```

Each entity page becomes a thin config + route file (~30-50 lines), not a full component.

### Composable cards

v2.5 entity cards each reimplement the same layout: image/preview, title, metadata chips, overlay badges, hover actions.

**Rule:** Build from shared primitives:

```
<EntityCard>
  <EntityCard.Preview />      // image, video preview, lazy loading
  <EntityCard.Body>
    <EntityCard.Title />
    <EntityCard.Metadata />   // chips, tags, rating
  </EntityCard.Body>
  <EntityCard.Actions />      // hover/long-press action menu
  <EntityCard.SelectCheckbox />
</EntityCard>
```

Per-entity cards compose these pieces — they don't rebuild them.

### Composable detail pages

Same principle. Detail pages follow a pattern: hero section, tabbed content, metadata grid, related entities. Build shared layout primitives:

```
<DetailPage>
  <DetailPage.Hero />         // cover image, title, actions
  <DetailPage.Tabs>
    <DetailPage.Tab />        // lazy-loaded tab content
  </DetailPage.Tabs>
  <DetailPage.MetadataGrid /> // key-value pairs
  <DetailPage.Related />      // linked entity cards
</DetailPage>
```

### Forms without formik

v2.5 uses formik everywhere. It's heavy, has stale-closure footguns with React 19, and the forms aren't complex enough to need it.

**Rule:** Use controlled components with a simple `useForm`-style hook (or react-hook-form if we find we need validation). Edit dialogs share a `<FieldGroup>` component for consistent label/input/error layout.

### Colocate, don't centralize

- **Hooks** live next to the components that use them, not in a global `hooks/` folder (exception: truly app-wide hooks like `useBreakpoint`, `useConfig`)
- **Types** are inferred from GraphQL codegen, not manually redeclared
- **Constants** live in the module that owns them
- **CSS** is Tailwind utility classes inline, not separate SCSS files (exception: complex animations)

### No implicit any, no lint suppressions

v2.5 has ~280 implicit `any` parameters (TS7006/TS7031). The v3 tsconfig has `strict: true`.

**Rule:** Every function parameter is typed. No `// eslint-disable` without a comment explaining why. No `as any` escapes — fix the type instead.

### No monoliths — small, focused modules

v2.5 has multiple 1000-2500 line files (`StashService.ts`, `SceneFilterBuilderDialog.tsx`, `SettingsInterfacePanel.tsx`, `SceneList.tsx`). These are hard to review, test, and maintain.

**Rule:** No single component file exceeds ~500 lines. If it does, split it — extract sub-components, hooks, or utilities into sibling files. The filter builder (2354 lines) gets split into `FilterBuilder.tsx` + `GroupEditor.tsx` + `ConditionEditor.tsx`. Settings panels each get their own file. List pages are thin configs, not fat components.

CSS follows the same principle: no SCSS files. Tailwind utility classes inline, colocated with the component. Complex shared styles (depth colors, animations) go in `globals.css` as CSS custom properties, not in sprawling per-component stylesheets.

### Per-view GraphQL fragments — fetch only what you need

v2.5 overuses heavyweight fragments like `SlimSceneData` everywhere — list views, cards, detail pages, related-entity panels all pull the same bloated fragment with dozens of fields, most of which any given view ignores. This wastes bandwidth, slows queries, and inflates the Apollo cache.

**Rule:** Each view defines its own fragment that requests exactly the fields it renders:

```graphql
# Card view — minimal fields for the grid
fragment SceneCardData on Scene {
  id title date rating100
  paths { screenshot preview }
  studio { id name }
  files { basename duration size height }
}

# Detail view — full fields for the detail page
fragment SceneDetailData on Scene {
  ...SceneCardData
  details director code
  performers { id name }
  tags { id name }
  groups { group { id name } }
  galleries { id title }
  # ...
}
```

Compose fragments with `...spread` when a larger view genuinely needs a smaller view's fields. Never use a "god fragment" that satisfies every consumer. The codegen will produce precise TypeScript types per fragment, so components get compile-time guarantees that they only access fields they requested.

### Toggles over checkboxes for on/off settings

v2.5 uses checkboxes for most boolean settings. Checkboxes are semantically correct for "agree to terms" or multi-select scenarios, but for on/off feature toggles they're visually unclear — the user can't tell at a glance whether the feature is active.

**Rule:** Use shadcn `Switch` (toggle) for binary on/off settings (enable/disable a feature, show/hide a panel). Reserve `Checkbox` for multi-select lists, bulk-edit indeterminate states, and actual checkbox semantics (terms acceptance, "also delete files"). When in doubt: if the label reads "Enable X" or "Show X", it's a toggle.

### Mobile-first responsive design

Every component is built mobile-first. Desktop layout is additive via Tailwind breakpoint modifiers (`md:`, `lg:`). No separate "mobile" and "desktop" component trees — one component that adapts.

**File to create:** `src/components/forms/useEntityForm.ts`

```tsx
function useEntityForm<T extends Record<string, unknown>>(initialValues: T) {
  const [values, setValues] = useState(initialValues);
  const [dirty, setDirty] = useState(false);

  const setValue = useCallback(<K extends keyof T>(key: K, value: T[K]) => {
    setValues(prev => ({ ...prev, [key]: value }));
    setDirty(true);
  }, []);

  const reset = useCallback(() => {
    setValues(initialValues);
    setDirty(false);
  }, [initialValues]);

  return { values, setValue, dirty, reset };
}
```

For validation, use native HTML validation (`required`, `pattern`, `min`/`max`) plus custom validation at submit time. Only add react-hook-form if validation logic gets genuinely complex.

**StashBox query pattern:**

- `ScrapeSingleStudioDocument` — scrape studio by name from a StashBox endpoint
- `ScrapeSingleTagDocument` — scrape tag by name from a StashBox endpoint

All use `fetchPolicy: "network-only"` since StashBox results should never be cached.

- `StashBoxBatchPerformerTag(input: StashBoxBatchTagInput!)` — batch match performers
- `StashBoxBatchStudioTag(input: StashBoxBatchTagInput!)` — batch match studios
- `StashBoxBatchTagTag(input: StashBoxBatchTagInput!)` — batch match tags

**Match result application:**
- User reviews side-by-side diff (local vs remote metadata)
- Accepts/rejects individual fields
- On save: calls entity update mutation (e.g. `PerformerUpdate`) with accepted fields
- Cache update: writes updated entity to Apollo cache via `store.writeQuery`

**Key patterns:**
- StashBox endpoint selection from `configuration.general.stashBoxes[]`
- Shows side-by-side comparison of local vs remote metadata
- User accepts/rejects individual field matches

## Phase 10: PWA & polish

### 10a. Service worker

**File to create:** `src/sw.ts` (registered from `main.tsx`)

Strategy:
- **Static assets** (JS, CSS, images, fonts): cache-first with versioned cache name
- **GraphQL API**: network-first with 5s timeout, falls back to cache
- **Media files** (video, thumbnails): cache-first (immutable by content hash)

Use Workbox (via `vite-plugin-pwa`) for service worker generation.

### 10b. Offline support

- Show offline indicator banner when `navigator.onLine` is false
- Cached list pages remain browsable offline
- Detail pages with cached data remain viewable
- Mutations queue and replay when connectivity returns (stretch goal)

### 10c. Install prompt

- PWA manifest (`public/manifest.json`) with app name, icons, theme color
- Custom install prompt UI (intercept `beforeinstallprompt` event)

### 10d. Touch gestures
